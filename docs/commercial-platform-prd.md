# 多商户预约平台商业化需求文档

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 方案确认稿 |
| 版本 | v0.1 |
| 更新日期 | 2026-07-15 |
| 产品形态 | 多商户、多门店预约 SaaS |
| 首期建议行业 | 展厅、体验馆、活动空间 |
| 后续行业模板 | 餐厅、咖啡店、工作室、美容与私人服务 |

## 1. 文档目的

本文件用于定义从“和 QQ 的周末小冒险”个人预约页面升级为可向商户销售的预约管理平台所需的产品能力、角色权限、业务规则、状态模型、数据边界、支付扩展和交付阶段。

本阶段只确认需求，不代表所有功能同时进入第一期开发。功能按以下优先级标记：

- `P0`：商业 MVP 必须具备。
- `P1`：正式销售和日常运营的重要增强。
- `P2`：规模化、行业深化或增值能力。

## 2. 产品愿景

为中小型线下商户提供一套容易配置、视觉友好、无需自行开发的预约与到店管理工具。商户可以在后台管理开放时间、容量、预约主题、人员、通知和品牌页面；消费者可以在手机端快速完成预约、验证、支付和签到。

平台应同时满足三个目标：

1. 消费者预约过程简单、有品牌感，尽量减少放弃。
2. 商户能够控制容量、人员和通知，降低人工沟通成本。
3. 平台能够隔离管理多个商户，并通过订阅、增值功能或交易服务实现收入。

## 3. 产品边界

### 3.1 本产品负责

- 商户和门店管理
- 预约主题与品牌页面配置
- 开放时间、时段、容量和资源管理
- 消费者登记、验证、预约、改期、取消和签到
- 商户员工权限与操作审计
- 邮件、短信等通知编排
- 预约订金或全款支付扩展
- 经营数据、客户记录和导出
- 商户套餐、试用、配额和平台账单

### 3.2 首期不负责

- 餐厅 POS、点餐、库存和后厨系统
- 完整员工工资、考勤和复杂排班
- 身份证、人脸等高敏感实名验证
- 平台代替商户提供线下商品或服务
- 自建资金清算、银行卡结算或支付通道
- 大型活动的选座票务和座位图编辑

## 4. 目标客户与场景

| 行业 | 典型预约主题 | 关键差异 |
| --- | --- | --- |
| 展厅/画廊 | 展览参观、团体讲解、VIP 预览 | 人数容量、讲解员、签到核销 |
| 体验馆 | 手作体验、品鉴、试驾、沉浸活动 | 时长、材料容量、订金 |
| 活动空间 | 开放日、沙龙、工作坊 | 名单、候补、批量通知 |
| 餐厅/咖啡店 | 正餐、下午茶、包间 | 桌位、人数、用餐时长、订金 |
| 工作室/私人服务 | 摄影、咨询、美容、课程 | 服务人员、房间、连续时间 |

建议首期以展厅、体验馆和活动空间为验证场景。底层数据模型保留资源能力，餐厅模板在第二阶段增加桌位和包间分配规则。

## 5. 核心概念

| 概念 | 定义 |
| --- | --- |
| 平台 | 运营所有商户的 SaaS 产品本身 |
| 商户 | 独立购买和使用平台的企业或个人经营主体 |
| 门店 | 商户下的具体营业地点，可有多个 |
| 预约主题 | 消费者可预约的服务或活动，如“周末看展” |
| 资源 | 被预约占用的对象，如桌位、房间、员工或讲解员 |
| 时段 | 某主题在某门店可预约的具体开始时间 |
| 容量 | 时段允许的预约单数、人数或资源数 |
| 预约 | 一次消费者提交的业务记录 |
| 到场人 | 同一预约下登记的参与人员 |
| 商户成员 | 可以登录商户后台的负责人或员工 |

## 6. 角色与权限

### 6.1 平台角色

| 角色 | 权限 |
| --- | --- |
| 平台超级管理员 | 管理全部商户、套餐、支付、风控、系统配置和平台成员 |
| 平台运营 | 审核商户、处理支持工单、查看脱敏业务数据和运营报表 |
| 平台财务 | 查看平台订阅、交易汇总、退款和对账数据 |
| 平台客服 | 查询预约状态、协助商户处理问题，不可修改支付配置 |

### 6.2 商户角色

| 角色 | 权限 |
| --- | --- |
| 商户所有者 | 全部商户权限、套餐、支付账户、成员和关闭商户 |
| 商户管理员 | 门店、主题、时间、预约、客户、通知和报表 |
| 接待员 | 查看和编辑预约、签到、改期、取消、内部备注 |
| 服务人员 | 查看分配给自己的预约和到场信息 |
| 只读成员 | 查看日历和报表，不可修改 |

`P0-RBAC-01` 所有商户后台请求必须同时校验登录身份、商户成员关系和具体权限。

`P0-RBAC-02` 商户成员只能访问所属商户的数据；拥有多个商户权限时需要显式切换商户。

`P1-RBAC-03` 商户所有者可以创建自定义角色并组合权限。

`P1-RBAC-04` 修改开放时间、容量、成员、支付、退款和预约状态必须记录审计日志。

## 7. 商户入驻与组织管理

### 7.1 商户入驻

`P0-ORG-01` 平台管理员可以手工创建商户并发送负责人邀请邮件。

`P0-ORG-02` 商户资料包括名称、Logo、联系人、联系电话、时区、默认语言和经营状态。

`P1-ORG-03` 支持商户自助注册、邮箱验证、试用期和套餐选择。

`P1-ORG-04` 支持平台审核、驳回、暂停和恢复商户。

`P2-ORG-05` 支持支付服务商模式下的商户资质进件和审核状态同步。

### 7.2 多门店

`P0-STORE-01` 一个商户可以创建一个或多个门店。

`P0-STORE-02` 门店资料包括名称、地址、电话、地图信息、时区、营业说明和到店指引。

`P0-STORE-03` 预约主题可以适用于一个或多个门店，并允许门店覆盖默认时间和容量。

`P1-STORE-04` 支持门店临时停业、永久关闭和数据归档。

## 8. 预约主题管理

`P0-SERVICE-01` 商户可以创建、编辑、复制、上下架和排序预约主题。

`P0-SERVICE-02` 主题配置至少包含：

- 名称、短描述和详细说明
- 封面图和主题图标
- 适用门店
- 预约时长和时段间隔
- 免费、到店付款、订金或全款模式
- 单笔最少与最多人数
- 提前开放天数和最晚预约时间
- 最早取消时间和取消说明
- 消费者填写字段
- 成功页文案和通知模板

`P0-SERVICE-03` 主题下架后不再接受新预约，但历史预约仍可查看和处理。

`P1-SERVICE-04` 支持主题分类、标签和列表页筛选。

`P1-SERVICE-05` 支持主题级自定义协议、注意事项和预约前勾选确认。

`P2-SERVICE-06` 支持附加项目，如套餐升级、饮品、材料包或额外人员费用。

## 9. 开放时间与时段

### 9.1 周期规则

`P0-SCHEDULE-01` 商户可以按星期配置重复开放时间，并为不同预约主题设置不同规则。

`P0-SCHEDULE-02` 支持开始时间、结束时间、时段间隔、服务时长和跨午夜场次。

`P0-SCHEDULE-03` 系统根据规则自动生成未来可预约时段，不要求商户逐日创建。

### 9.2 日期例外

`P0-SCHEDULE-04` 支持指定日期关闭、缩短时间、临时加场和修改容量。

`P0-SCHEDULE-05` 日期例外优先于每周重复规则。

`P1-SCHEDULE-06` 支持批量设置法定节假日和日期范围。

`P1-SCHEDULE-07` 修改已有预约的时段规则时，系统必须提示受影响预约，不可静默删除。

### 9.3 预约窗口

`P0-SCHEDULE-08` 支持“最多提前多少天预约”和“开始前多久停止预约”。

`P1-SCHEDULE-09` 支持按会员等级或邀请链接提前开放预约。

## 10. 容量与资源

### 10.1 容量模式

`P0-CAPACITY-01` 每个时段至少支持以下两种容量：

- 最大预约单数，例如同一时间最多 5 组。
- 最大接待人数，例如同一时间最多 30 人。

`P0-CAPACITY-02` 创建或修改预约时，系统必须原子校验并扣减容量，避免并发超卖。

`P0-CAPACITY-03` 取消、支付超时或管理员释放预约后，容量自动返还。

`P0-CAPACITY-04` 商户可以手工关闭时段，但已有预约不会被自动取消。

### 10.2 资源模式

`P1-RESOURCE-01` 支持创建资源类型和资源实例，例如“包间 A”“讲解员 1”“摄影棚 B”。

`P1-RESOURCE-02` 预约主题可以要求一个或多个资源，并按时长锁定资源。

`P1-RESOURCE-03` 系统可以自动分配满足条件的资源，商户也可手工调整。

`P2-RESOURCE-04` 餐厅模板支持桌位人数范围、拼桌规则、组合桌和包间最低消费。

## 11. 消费者预约流程

### 11.1 进入预约页

`P0-BOOKING-01` 每个商户拥有独立公开预约地址，可分享至微信、短信和社交平台。

`P0-BOOKING-02` 页面优先适配手机端，并展示商户品牌、门店、主题、价格和可预约状态。

`P0-BOOKING-03` 页面支持按主题、门店或指定活动直达，减少重复选择步骤。

### 11.2 填写与验证

`P0-BOOKING-04` 消费者选择主题、门店、日期、时段和人数后填写预约资料。

`P0-BOOKING-05` 商户可以配置姓名、手机、邮箱、公司、备注等字段是否显示和是否必填。

`P0-BOOKING-06` 系统必须展示隐私说明和商户取消规则。

`P1-VERIFY-01` 商户可以开启手机号短信验证码或邮箱验证码。

`P1-VERIFY-02` 同一手机号、邮箱、IP 或设备的验证码与预约频率需要限流。

`P1-VERIFY-03` 高风险预约可以进入人工确认状态，而不是直接成功。

### 11.3 提交结果

`P0-BOOKING-07` 免费预约提交成功后生成不可预测的预约编号和核销码。

`P0-BOOKING-08` 需要支付时先创建临时占位，并展示剩余支付时间。

`P0-BOOKING-09` 成功页展示主题、时间、地点、人数、预约人、规则和预约编号。

`P0-BOOKING-10` 消费者可以保存凭证、加入系统日历和分享预约信息。

`P1-BOOKING-11` 消费者可以通过安全链接查看、改期或取消预约，无需注册账户。

`P2-BOOKING-12` 支持消费者账户，用于查看跨商户历史预约和会员权益。

## 12. 预约管理后台

`P0-ADMIN-01` 提供日历视图和列表视图，并支持按门店、主题、状态、时间和员工筛选。

`P0-ADMIN-02` 商户成员可以手工新增预约，用于电话、现场和其他渠道。

`P0-ADMIN-03` 可以查看预约详情、到场人、通知记录、支付记录和内部操作历史。

`P0-ADMIN-04` 可以改期、修改人数、取消、确认、签到、完成和标记爽约。

`P0-ADMIN-05` 改期或增加人数时必须重新校验目标时段容量。

`P0-ADMIN-06` 内部备注不向消费者展示，消费者备注不可被商户无痕覆盖。

`P1-ADMIN-07` 支持批量确认、批量取消、批量通知和导出。

`P1-ADMIN-08` 支持打印当日名单和签到表。

`P2-ADMIN-09` 支持拖拽改期，但保存时仍需执行容量和权限校验。

## 13. 到场人员与签到

`P0-GUEST-01` 一笔预约至少有一名主要联系人和一个预约人数。

`P1-GUEST-02` 商户可以要求逐人登记姓名、联系方式或自定义字段。

`P1-CHECKIN-01` 每笔已确认预约生成二维码或短核销码。

`P1-CHECKIN-02` 接待员可以扫码、输入预约编号或按姓名搜索签到。

`P1-CHECKIN-03` 支持整单签到和逐人签到，并记录操作人和时间。

`P1-CHECKIN-04` 重复核销时必须提示首次核销信息，不能静默重复成功。

## 14. 候补、取消与爽约

`P1-WAITLIST-01` 时段满员后可以允许消费者加入候补名单。

`P1-WAITLIST-02` 容量释放后按顺序通知候补者，并给予限时确认窗口。

`P1-CANCEL-01` 商户可以配置免费取消截止时间、不可取消时间和退款比例。

`P1-CANCEL-02` 消费者取消前必须看到退款金额和容量释放结果。

`P1-NOSHOW-01` 商户可以标记爽约，并在客户记录中显示次数。

`P2-NOSHOW-02` 商户可以针对高爽约客户要求订金或人工确认。

## 15. 通知中心

### 15.1 通知渠道

`P0-NOTIFY-01` 首期支持邮件通知消费者和一个或多个商户收件人。

`P0-NOTIFY-02` 通知场景包括预约创建、确认、改期、取消和商户提醒。

`P1-NOTIFY-03` 增加短信通知和开始前提醒。

`P2-NOTIFY-04` 增加微信公众号、企业微信、飞书或其他企业渠道。

### 15.2 模板与可靠性

`P0-NOTIFY-05` 通知模板支持商户名称、预约人、主题、时间、地址、人数和管理链接等变量。

`P0-NOTIFY-06` 每次发送必须记录渠道、接收方、模板、状态、失败原因和重试次数。

`P0-NOTIFY-07` 通知失败不应回滚已经成功创建的预约，但后台必须显示失败并允许重发。

`P1-NOTIFY-08` 商户可以自定义邮件标题、正文、署名和提醒时间。

## 16. 品牌页面与模板

`P0-BRAND-01` 商户可以上传 Logo、封面，配置品牌名称、主色、辅助色和联系信息。

`P0-BRAND-02` 平台提供至少三种预约页面模板：童话活动、简洁展厅、餐饮门店。

`P0-BRAND-03` 模板只改变展示层，不得改变预约、容量和支付规则。

`P1-BRAND-04` 支持商户子域名，例如 `brand.platform.example`。

`P1-BRAND-05` 付费套餐支持绑定自定义域名和移除平台品牌。

`P2-BRAND-06` 支持模板市场、行业模板复制和平台代配置服务。

现有“和 QQ 的周末小冒险”应保留为第一套可复用主题模板，而不是继续承担业务数据和邮件逻辑。

## 17. 客户记录与 CRM

`P1-CRM-01` 系统按商户维度聚合客户历史预约，不跨商户共享客户资料。

`P1-CRM-02` 商户可以添加客户标签、内部备注、偏好和黑名单状态。

`P1-CRM-03` 客户详情显示预约次数、取消次数、爽约次数和累计消费。

`P1-CRM-04` 黑名单规则必须区分禁止预约、要求人工确认和要求订金。

`P2-CRM-05` 支持会员等级、优惠券、生日和复访提醒。

## 18. 日历与外部集成

`P0-CALENDAR-01` 消费者可以下载标准 `.ics` 日历文件。

`P1-CALENDAR-02` 商户可以订阅门店或个人预约日历。

`P1-CALENDAR-03` 支持 Google Calendar、Outlook 等日历同步，明确单向或双向同步范围。

`P2-INTEGRATION-01` 提供 Webhook 和开放 API，允许商户连接 CRM、POS 或自动化工具。

`P2-INTEGRATION-02` Webhook 必须签名、可重试并提供发送日志。

## 19. 支付与退款

### 19.1 两类支付关系

平台必须将以下两类支付分开建模和对账：

1. 商户向平台支付的软件订阅费。
2. 消费者向商户支付的预约订金或服务费用。

### 19.2 消费者预约支付

`P1-PAY-01` 预约主题支持免费、订金、全款和到店付款。

`P1-PAY-02` 支付金额必须由服务端根据主题、人数和附加项目计算，不能信任前端金额。

`P1-PAY-03` 支付订单与预约分离，记录支付渠道、商户订单号、渠道订单号、金额和状态。

`P1-PAY-04` 只有经过验签的支付平台异步回调才能将预约确认为已支付。

`P1-PAY-05` 创建支付请求时使用幂等键，重复提交不得产生多笔有效订单。

`P1-PAY-06` 支付占位超时后释放容量；迟到回调进入异常处理，不得直接造成超卖。

`P1-REFUND-01` 支持全额和部分退款，并记录退款原因、操作人和渠道状态。

`P1-REFUND-02` 退款失败时预约和支付状态必须保持可追踪，允许人工重试。

### 19.3 支付接入策略

国内市场优先采用商户自行收款或支付服务商下的特约商户模式，使预约款直接结算至商户。微信支付要求商户或服务商完成对应入驻和参数准备；支付宝服务商能力面向完成企业认证的服务商主体。接入前需要结合实际经营主体、地区和业务模式确认资质。

- 微信支付服务商文档：https://pay.wechatpay.cn/doc/v3/partner/4012062375
- 支付宝服务商平台：https://partner.alipay.com/

海外市场可以评估 Stripe Connect，由商户作为 Connected Account 接受消费者付款，并明确商户记录主体、退款、争议和平台费用责任。

- Stripe Connect：https://docs.stripe.com/connect

支付能力上线前必须由支付服务商、财务和法律顾问确认资金流、商户协议、退款和发票责任。

## 20. 商户套餐与平台商业化

`P1-BILLING-01` 平台支持试用、月付和年付套餐。

`P1-BILLING-02` 套餐可以限制门店数、成员数、月预约量、通知量、模板、自定义域名和高级报表。

`P1-BILLING-03` 超过配额前进行提醒，达到限制后的行为必须明确，不可直接丢失预约。

`P1-BILLING-04` 支持升级、降级、续费失败、宽限期和暂停服务。

`P1-BILLING-05` 商户可以查看账单、订阅状态和付款记录。

`P2-BILLING-06` 支持按预约量计费、短信包、定制模板和实施服务等增值收入。

建议初始套餐结构：

| 套餐 | 目标客户 | 核心差异 |
| --- | --- | --- |
| 试用版 | 新商户体验 | 单门店、有限预约量、平台品牌 |
| 基础版 | 小型门店 | 基础预约、邮件、导出 |
| 专业版 | 多员工门店 | 短信、二维码、自定义域名、报表 |
| 企业版 | 多门店品牌 | 权限、API、专属支持和定制能力 |

具体价格在完成首批访谈和成本测算后确定，本需求文档不锁定金额。

## 21. 数据分析与报表

`P1-REPORT-01` 商户首页展示今日预约、待确认、已取消、已签到和剩余容量。

`P1-REPORT-02` 报表至少包含预约量、预约人数、取消率、爽约率、到店率和时段利用率。

`P1-REPORT-03` 支持按时间、门店、主题和来源筛选。

`P2-REPORT-05` 支持预约转化漏斗、复访率、收入和渠道效果。

`P2-REPORT-06` 平台运营可以查看聚合商户指标，但默认不读取商户客户明细。

## 22. 平台运营后台

`P0-PLATFORM-01` 平台可以查看商户状态、套餐、门店数、成员数和预约使用量。

`P0-PLATFORM-02` 可以创建、暂停、恢复和归档商户。

`P0-PLATFORM-03` 客服查询商户问题时需要明确授权和审计记录。

`P1-PLATFORM-04` 支持功能开关，按套餐、商户或灰度范围启用新功能。

`P1-PLATFORM-05` 提供通知失败、支付异常、容量冲突和任务积压监控。

`P1-PLATFORM-06` 支持商户公告、系统维护通知和客服工单。

`P2-PLATFORM-07` 支持商户健康度、流失风险和套餐升级机会分析。

## 23. 数据模型

核心实体建议如下：

| 实体 | 关键内容 |
| --- | --- |
| Tenant | 商户、状态、套餐、默认时区 |
| Store | 门店、地址、联系方式、时区 |
| User | 登录用户基础身份 |
| Membership | 用户与商户的角色和权限 |
| BookingService | 预约主题、时长、价格、规则 |
| ScheduleRule | 每周重复开放规则 |
| ScheduleException | 特定日期关闭、加场或覆盖 |
| Resource | 桌位、房间、员工等资源 |
| SlotInventory | 时段的单数、人数和资源库存 |
| Booking | 预约主记录、状态、人数、来源 |
| Guest | 到场人员登记 |
| Customer | 商户维度的客户档案 |
| Payment | 支付订单与渠道状态 |
| Refund | 退款请求和结果 |
| Notification | 通知内容、渠道和投递状态 |
| CheckIn | 签到、核销和操作人员 |
| AuditLog | 重要后台操作记录 |
| Subscription | 商户套餐与续费状态 |

所有商户业务实体必须包含不可为空的 `tenant_id`。服务端查询不能依赖前端传入商户编号决定访问范围，必须从已验证的成员身份推导。

## 24. 状态模型

### 24.1 预约状态

```text
DRAFT 草稿
  -> HOLDING 占位中
  -> PENDING_PAYMENT 待支付
  -> PENDING_CONFIRMATION 待商户确认
  -> CONFIRMED 已确认
  -> CHECKED_IN 已签到
  -> COMPLETED 已完成

任意允许节点
  -> CANCELLED 已取消
  -> EXPIRED 已过期
  -> NO_SHOW 爽约
```

每一次状态变化都必须校验允许的来源状态，并写入状态历史。禁止通过任意数据库更新跳过业务规则。

### 24.2 支付状态

```text
CREATED 已创建
  -> PENDING 待支付
  -> PAID 已支付
  -> PARTIALLY_REFUNDED 部分退款
  -> REFUNDED 已退款

异常状态：FAILED 支付失败 / CLOSED 已关闭 / REVIEW_REQUIRED 待人工处理
```

预约状态与支付状态不能合并成一个字段。例如预约已取消时，支付可能仍处于退款中。

## 25. 安全、隐私与合规

`P0-SEC-01` 商户数据必须在服务端强制隔离，并为关键表设计租户级访问策略。

`P0-SEC-02` 密码不得自行明文存储；优先使用成熟身份服务或安全密码哈希方案。

`P0-SEC-03` 登录、验证码、预约提交、导出和支付接口必须限流。

`P0-SEC-04` 支付密钥、邮件密钥和短信密钥只能保存在服务端密钥系统中。

`P0-SEC-05` 日志不得记录完整验证码、支付密钥或不必要的客户敏感信息。

`P0-PRIVACY-01` 提供隐私政策、服务协议和商户数据处理条款。

`P0-PRIVACY-02` 只收集完成预约必需的信息，并记录字段收集目的。

`P1-PRIVACY-03` 支持客户资料查询、更正、导出、匿名化或删除流程。

`P1-PRIVACY-04` 商户可配置数据保留期限，超过期限后自动删除或匿名化。

`P1-SEC-06` 高权限账号支持双重验证和登录设备管理。

## 26. 非功能需求

### 26.1 性能

- `P0-NFR-01` 常规网络下，公开预约页主要内容应在 2.5 秒内可交互。
- `P0-NFR-02` 查询可预约时段的接口在正常负载下 P95 目标小于 500 毫秒。
- `P0-NFR-03` 提交预约必须有明确加载状态，避免重复点击。

### 26.2 可靠性

- `P0-NFR-04` 预约创建、容量扣减和支付占位必须在同一事务边界内保持一致。
- `P0-NFR-05` 邮件、短信和 Webhook 使用异步任务并支持指数退避重试。
- `P0-NFR-06` 数据库需要自动备份，并定期验证恢复流程。
- `P1-NFR-07` 正式付费版本的月度可用性目标不低于 99.9%。

### 26.3 兼容与可用性

- `P0-NFR-08` 消费者端优先支持主流手机浏览器和微信内置浏览器。
- `P0-NFR-09` 后台支持桌面和平板，不以手机作为复杂配置的主要设备。
- `P1-NFR-10` 界面满足基础无障碍要求，包括键盘操作、焦点、标签和颜色对比度。
- `P1-NFR-11` 时间数据统一以 UTC 存储并携带门店时区，展示时转换。
- `P2-NFR-12` 支持多语言和多币种展示。

### 26.4 可观测性

- `P0-NFR-13` 记录请求错误、后台任务失败、通知失败和支付异常。
- `P0-NFR-14` 关键链路使用关联 ID 串联预约、支付、通知和回调日志。
- `P1-NFR-15` 建立错误率、响应时间、任务积压和支付异常告警。

## 27. 商业 MVP 范围

第一期必须交付：

1. 平台管理员手工创建商户。
2. 商户登录、基础角色和成员邀请。
3. 多门店、预约主题和品牌基础设置。
4. 每周开放时间、日期例外和预约窗口。
5. 每时段预约单数与人数容量。
6. 手机端公开预约页和可配置表单。
7. 免费预约、核对、确认和日历文件。
8. 商户日历、预约列表、改期、取消、签到和备注。
9. 消费者与商户邮件通知、发送日志和重试。
10. 基础审计、限流、备份和平台监控。

第一期暂不交付：

- 消费者在线支付
- 资源自动分配
- 候补名单
- 短信和微信通知
- 客户账号和会员体系
- 商户自助订阅付款
- 自定义域名和开放 API

虽然第一期不启用支付，数据库仍应预留支付状态、订金规则和占位过期字段，避免后续破坏预约模型。

## 28. 分阶段路线

### 阶段 0：需求与设计确认

- 商户访谈和首个行业确认
- PRD、信息架构、原型和视觉系统
- 数据模型、权限模型和技术选型
- 邮件、短信和支付供应商调研

### 阶段 1：商业 MVP

- 多商户基础、预约引擎、容量、后台和邮件
- 使用首批真实商户进行封闭测试
- 现有童话页面迁移为主题模板

### 阶段 2：运营增强

- 二维码签到、候补、短信、客户记录、统计和多门店增强
- 餐厅资源模型、桌位与包间模板
- 子域名和自定义域名

### 阶段 3：支付与收费

- 预约订金、全款、退款、支付对账
- 商户试用、套餐、订阅和配额
- 支付商户进件与异常处理

### 阶段 4：平台化

- 开放 API、Webhook、模板市场和外部系统集成
- 企业权限、双重验证、多语言和高级报表

## 29. MVP 验收指标

建议在首批试点中观察：

| 指标 | 建议目标 |
| --- | --- |
| 预约创建成功率 | 不低于 99%（排除用户主动放弃） |
| 容量超卖 | 0 次 |
| 预约通知进入发送队列 | 不低于 99.9% |
| 商户独立完成时间配置 | 不低于 80% |
| 消费者移动端完成预约中位时间 | 小于 2 分钟 |
| 商户每日人工确认时间 | 相比原流程显著下降 |

最终商业指标应在首批商户使用两到四周后，根据真实基线重新确定。

## 30. 当前原型迁移策略

现有项目可以复用：

- 童话视觉模板
- 手机端分步预约交互
- 日期、活动和邀请函体验
- 图片导出、系统分享和日历文件

需要重构：

- 固定的 QQ 文案改为商户和主题配置
- 固定开放时间改为后台规则
- 浏览器直发 FormSubmit 改为服务端通知任务
- 前端状态改为数据库预约记录
- 随机预约编号改为安全、唯一且不可预测的编号
- 单页面逻辑拆分为消费者端、商户后台、平台后台和服务端 API
- 当前 OpenAI Sites 部署仅作为原型或模板展示，商业系统使用具备数据库、任务队列、密钥管理和监控的生产架构

## 31. 待确认事项

进入设计和开发前需要确认：

1. 首个重点行业是否按“展厅、体验馆和活动空间”推进。
2. 首期商户是否由平台人工开通，而不是开放自助注册。
3. 商业 MVP 是否完全不启用消费者支付，只预留数据结构。
4. 首期验证方式是否只做邮箱，还是同时采购短信验证码。
5. 是否从第一期支持多门店，还是首批每个商户限制单门店。
6. 是否需要在第一期加入二维码签到。
7. 首批预计商户数、单商户日预约量和高峰并发量。
8. 主要市场是否仅中国大陆，以决定支付、短信、地图和合规供应商。

这些事项确认后，下一份交付物应是后台信息架构、关键页面原型、数据库 ER 图、API 边界和商业 MVP 开发任务拆分。
