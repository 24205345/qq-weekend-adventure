# 商业 MVP 实施说明

## 1. 本轮交付

本轮完成了第一版多商户预约闭环，目标是让一个商户可以配置预约规则、分享公开链接、接收预约，并由员工在后台完成日常处理。

### 商户后台

后台地址为 `/admin`，使用 Sign in with ChatGPT 完成身份识别。首次登录且没有商户成员关系时，系统会为该用户自动创建一个试用商户、主门店、默认预约主题和基础开放时间。

后台模块：

- 经营概览：今日预约、待确认、即将到店和通知失败数量。
- 预约管理：筛选、手工录入、改期、改人数、确认、签到、完成、取消、爽约、内部备注和通知重发。
- 开放时间：按主题配置每周开放时间、指定时段、时段间隔、最大订单数和最大人数。
- 日期例外：指定日期关闭、临时加场或覆盖容量。
- 预约主题：门店、介绍、时长、单笔人数、提前开放、预约截止、确认方式和通知邮箱。
- 门店管理：名称、地址、电话和到店指引。
- 成员权限：所有者、管理员、接待员、服务人员和只读成员。
- 品牌设置：商户名称、品牌色、模板和公开预约地址。

### 消费者预约

公开地址格式为 `/book/<商户标识>`。消费者可以选择主题、门店、日期、时段、人数，填写姓名与联系方式后提交预约。

提交时服务端会：

1. 验证商户、门店、主题和开放规则。
2. 验证预约窗口、时段、单笔最大人数。
3. 同时检查该时段的剩余订单数和剩余人数。
4. 原子写入预约，避免并发超卖。
5. 生成不可预测的预约编号和管理令牌。
6. 记录预约事件、通知任务和后台审计信息。
7. 尝试向商户通知邮箱发送预约邮件。

预约成功页提供预约凭证、系统日历文件和系统分享。

### 现有童话模板

首页仍是“和 QQ 的周末小冒险”。它现在使用固定商户 `qq-weekend` 的数据库配置保存预约，不再只依赖邮件。服务端通知失败时，页面会保留原有浏览器邮件发送作为兼容回退。

## 2. 数据与权限

结构化数据保存在 OpenAI Sites 提供的 D1 数据库中。主要实体包括：

- 商户与成员关系
- 门店与预约主题
- 每周开放规则与日期例外
- 预约、状态事件和通知日志
- 后台操作审计日志

所有商户业务表包含 `tenant_id`。后台接口从已登录邮箱查询成员关系，并在服务端限定商户范围；不信任浏览器传入的商户编号。

角色规则：

- 所有者和管理员可以修改商户配置与成员。
- 接待员和服务人员可以处理预约。
- 只读成员只能查看，不能修改预约或配置。
- 所有者不能被普通成员管理接口停用。

## 3. 容量规则

每个开放规则同时配置：

- `maxBookings`：同一时段最多预约单数。
- `maxGuests`：同一时段最多预约人数。

预约创建和改期使用单条条件写入语句完成容量判断。取消或过期预约不占用容量；已确认、待确认、已签到和已完成记录仍保留历史。

每个请求带有租户范围内唯一的幂等键。网络重试不会创建两条相同预约。

## 4. 邮件通知

当前使用 FormSubmit 作为过渡邮件通道，并记录每次发送状态、错误和尝试次数。预约创建成功不依赖邮件成功，因此邮件供应商故障不会丢失预约。

正式商业试点前建议接入事务邮件供应商，并通过服务端密钥配置发送域名。届时需要增加：

- 消费者确认邮件
- 改期、取消和到店前提醒
- 后台任务重试与失败告警
- 邮件退信和投诉处理

## 5. 已知边界

本轮暂未实现：

- 消费者在线付款、订金和退款
- 消费者短信验证码
- 消费者自助改期或取消链接
- 二维码扫码核销
- 候补名单和资源自动分配
- 平台运营总后台与商户套餐收费
- 自定义域名、对象存储图片上传和外部日历双向同步

商户品牌图片仍使用项目内现有素材。商户上传 Logo、封面和场地图片需要在下一阶段接入对象存储。

## 6. 上线后首轮检查

1. 使用商户负责人邮箱登录 `/admin`。
2. 确认进入的是目标商户；若自动创建了新试用商户，需要将实际登录邮箱加入目标商户成员。
3. 在后台检查通知邮箱、开放时间、时段容量和公开预约链接。
4. 使用公开链接提交一笔测试预约。
5. 检查后台预约、剩余容量、邮件通知和状态操作。
6. 使用两个浏览器同时提交最后一个名额，确认只成功一笔。

## 7. 下一阶段建议

下一阶段优先处理消费者确认邮件、图片上传、平台运营后台和二维码签到；支付功能在商户入驻模式、资金流和退款责任确认后再接入。
